# 《决战苏富比》产品与技术设计规格

> 文档状态：设计已确认，等待实施计划审批  
> 最后更新：2026-09-01

> 本规格汇总已确认的产品范围和技术设计。详细游戏规则见 [`../../game-rules.md`](../../game-rules.md)，临时牌库见 [`../../data/placeholder-collections.json`](../../data/placeholder-collections.json)。

## 1. 项目目标

开发一款支持 3～8 名玩家在线开房游玩的《决战苏富比》微信小程序。首版以微信小程序发布为目标，支持实时竞拍、私密手牌与现金、公开藏品、阶段结算、断线重连和对局结果留存。

游戏规则以 [`docs/game-rules.md`](../../game-rules.md) 为唯一产品规则基线。

## 2. 已确认的整体架构

采用 **原生微信小程序 + Node.js 权威游戏服务端 + 微信云托管 + MySQL + Redis**。

### 2.1 微信小程序客户端

- 使用微信原生小程序框架；
- 业务代码使用 TypeScript；
- 负责页面展示、动画、倒计时显示和玩家操作采集；
- 通过 HTTPS 完成登录、创建房间、加入房间、历史对局等普通请求；
- 通过 WebSocket 接收实时游戏状态并提交竞拍操作；
- 客户端不自行决定成交、扣款、结算或主持权流转结果。

### 2.2 Node.js 权威游戏服务端

- 使用 Node.js 与 TypeScript；
- 服务端是游戏状态与规则判定的唯一权威；
- 负责身份验证、房间管理、座次、发牌、竞拍状态机、服务端计时器、现金转移、阶段结算和最终排名；
- 客户端只提交操作意图，例如出价、放弃、购买、选择藏品或响应联合邀请；
- 服务端校验操作是否合法后更新状态，并向玩家广播经过权限过滤的结果；
- 所有随机行为由服务端产生并记录，客户端不得决定发牌或随机结果。

### 2.3 实时通信

- 游戏进行中的主要通信方式为 WebSocket；
- 服务端维护权威倒计时，客户端倒计时只用于展示；
- 房间内的公开变化通过 WebSocket 广播；
- 私密手牌、现金和暗标报价只发送给有权限的玩家；
- 连接恢复后，客户端重新获取服务端当前状态，而不是依赖本地缓存继续推演。

### 2.4 数据存储

#### MySQL

用于持久化：

- 微信用户与玩家资料；
- 房间及参与者记录；
- 对局基础信息；
- 对局最终结果与排名；
- 藏品固定配置；
- 需要长期保留的关键操作和结算记录。

#### Redis

用于保存和协调活跃对局：

- 当前房间状态；
- 玩家在线状态与连接映射；
- 当前主持人和操作人；
- 当前竞拍状态；
- 服务端倒计时及超时任务；
- 必要的并发控制与幂等标记。

### 2.5 部署与资源

- 服务端部署在微信云托管；
- 对外提供 HTTPS 与 WSS 接口；
- 藏品图片等静态资源使用对象存储和 CDN；
- 服务端实例应尽量保持无状态，可从 Redis/MySQL 恢复活跃对局；
- 不依赖创建房间的玩家持续在线，房主掉线不影响服务端推进游戏。

## 3. 核心设计原则

1. **服务端权威**：任何影响胜负的规则均由服务端执行。
2. **信息隔离**：每个玩家只能看到自己的现金、手牌和暗标内容。
3. **确定性规则引擎**：同样的状态和操作必须产生同样的结果。
4. **可恢复**：客户端断线后能够恢复当前房间、阶段、拍卖和倒计时状态。
5. **可审计**：关键操作和现金变化应有可追踪的事件记录。
6. **防重复操作**：网络重试不得导致重复出价、重复扣款或重复发牌。
7. **配置与逻辑分离**：84 张藏品的数据配置独立于游戏规则代码。
8. **先实现核心玩法**：首版不引入非必要的社交、商城或成长系统。

## 4. 对局状态、事件日志与恢复

采用 **快照 + 事件日志** 的混合方案。

### 4.1 活跃状态快照

Redis 保存每个活跃房间的最新权威状态，至少包括：

- 房间状态、玩家座次与在线状态；
- 当前阶段、当前主持人和当前操作人；
- 玩家现金净余额、私密手牌和公开已购藏品；
- 剩余藏品库与已经作废的藏品；
- 五个收藏系列的本阶段数量、累计单价和历史排名；
- 当前竞拍类型、参与者、已提交操作和服务端截止时间；
- 联合拍卖中的旧主持人、新主持人和两张藏品；
- 当前房间最新事件序号与状态版本号。

客户端不能直接读取完整快照。服务端必须根据接收者身份生成公开视图和个人私密视图，避免泄露他人现金、手牌和暗标报价。

### 4.2 事件日志

MySQL 持久化影响游戏结果的关键事件，每个事件至少包含：

- 全局唯一事件 ID；
- 房间 ID；
- 对局 ID；
- 严格递增的房间事件序号；
- 操作请求 ID；
- 事件类型；
- 发起玩家；
- 服务端发生时间；
- 规则引擎版本；
- 事件负载与必要的结算结果。

关键事件包括但不限于：玩家加入、准备、游戏开始、发牌、打出藏品、报价、放弃、超时、联合邀请与响应、拍卖成交、现金转移、阶段结束、藏品回收、失窃罚款、负债冲抵、主持权变更和游戏结束。

暗标报价虽然需要留存以便审计，但在暗标揭晓前不得通过房间广播、查询接口或日志展示泄露给其他玩家。

### 4.3 命令、幂等与并发控制

- 客户端每次操作携带唯一的 `requestId` 和它已知的 `stateVersion`；
- 服务端先验证玩家身份、房间阶段、操作权限、截止时间、现金和状态版本；
- 同一个 `requestId` 重复到达时返回第一次处理结果，不重复执行；
- 每个房间的状态变更必须串行执行，防止同时出价或超时任务造成双重成交；
- 每次合法状态变更递增 `eventSequence` 和 `stateVersion`；
- 过期操作、越权操作或基于旧状态提交的冲突操作必须被拒绝，并返回最新可见状态。

### 4.4 快照持久化策略

- Redis 在每次合法状态变更后更新最新活跃快照；
- MySQL 持久化全部关键事件；
- 游戏开始、每次拍卖成交、阶段结算完成和游戏结束后，将完整权威快照持久化至 MySQL；
- 服务端还可按固定事件数量生成周期快照，以限制故障恢复时需要重放的事件数量；
- 已完成对局的最终快照、排名和结算摘要长期保存在 MySQL；
- Redis 中已结束或长期无活动房间的数据可在持久化确认后按过期策略清理。

### 4.5 断线重连

1. 玩家使用同一微信身份重新连接；
2. 服务端验证玩家属于该房间，并重新绑定当前连接；
3. 服务端读取最新权威快照；
4. 如果持久化快照落后，则按事件序号重放后续事件；
5. 服务端根据玩家身份生成完整的个人可见状态；
6. 客户端使用该状态整体覆盖本地状态，并根据服务端截止时间恢复倒计时显示。

客户端重连后不补发已经失效的操作，也不能依据离线前的本地倒计时自行判定结果。

### 4.6 故障恢复与一致性

- 规则状态变更、事件记录和快照更新由服务端统一协调；
- 若进程异常退出，新实例从最新持久化快照及后续事件恢复房间；
- 超时任务必须具有唯一标识并可重复调度，重复触发时只能有一次生效；
- 如果客户端显示与服务端不一致，始终以服务端状态为准；
- 现金变化必须记录来源、去向、变更前余额和变更后余额，以便审计负债冲抵及联合拍卖分账。

## 5. 房间与开局流程

### 5.1 创建和加入房间

- 玩家登录后可以创建新房间，或输入 **6 位房间号**加入已有房间；
- 房间号由服务端生成，并保证在有效期内唯一；
- 房主可以通过微信分享卡片邀请好友，分享卡片携带房间标识；
- 玩家通过分享卡片进入小程序后，完成登录并直接尝试加入对应房间；
- 每个房间最少 3 人、最多 8 人；达到 8 人后拒绝新的玩家加入；
- 游戏开始后锁定房间，不允许新玩家加入，只允许本局原有玩家重连。

### 5.2 房主与准备状态

- 创建房间的玩家成为初始房主；
- 房主身份只用于游戏开始前的房间管理，不参与游戏内主持人的确定；
- 非房主玩家加入后默认为未准备，需要主动点击“准备”；
- 非房主玩家在游戏开始前可以取消准备；
- 房主无需设置准备状态；
- 当房间达到至少 3 人，且所有非房主玩家均已准备时，房主可以开始游戏；
- 游戏开始请求由服务端再次校验人数、准备状态和房间状态，避免重复开始或越权开始。

### 5.3 开始前离开与移除

- 游戏开始前，任意非房主玩家可以主动离开房间；
- 房主可以在游戏开始前移除其他玩家；
- 被移除玩家失去该房间座位，可重新申请加入仍未开始且未满员的房间；
- 房主主动离开时，房主身份按当前座次顺时针移交给下一位玩家；
- 如果房间中只剩房主且房主离开，则房间人数降为 0，房间自动解散；
- 任意玩家加入、离开、被移除或房主变更后，服务端实时广播最新房间成员和准备状态。

### 5.4 游戏开始

房主发起开始游戏后，由服务端原子化执行以下操作：

1. 确认房间状态仍为等待中；
2. 确认玩家人数为 3～8 人；
3. 确认所有非房主玩家均已准备；
4. 锁定本局玩家名单和座次；
5. 创建正式对局记录；
6. 初始化固定藏品库并完成洗牌；
7. 为每名玩家发放对应数量的初始手牌；
8. 为每名玩家设置 150 万初始现金；
9. 随机选出首位游戏主持人；
10. 保存初始快照和开局事件；
11. 将房间切换为游戏中状态，并向所有玩家发送各自有权限查看的初始游戏状态。

### 5.5 房间生命周期

房间至少包含以下状态：

```text
等待加入 → 等待准备 → 游戏中 → 已结束
                    ↘ 已解散
```

- 等待中的空房间立即解散；
- 已开始的房间不能因房主或其他玩家掉线而解散；
- 游戏结束后保留结果记录，活跃房间资源按既定过期策略清理；
- 同一个玩家在同一时间只能加入一个尚未结束的对局，避免跨房间重复占位。

## 6. 微信登录与玩家资料

### 6.1 登录与会话

- 玩家首次进入小程序时，客户端调用 `wx.login` 获取临时登录凭证；
- 客户端将临时凭证发送给服务端，由服务端完成微信身份校验并建立或查找玩家账号；
- 同一微信身份只对应一个游戏玩家账号；
- 服务端签发游戏会话凭证，后续 HTTPS 与 WebSocket 请求均须携带有效身份凭证；
- 会话过期后，客户端重新执行登录流程，不依赖客户端自行保存微信身份信息；
- 首版不要求玩家授权手机号，拒绝手机号授权不影响任何核心游戏功能。

### 6.2 首次资料设置

首次进入游戏的玩家需要完成基础资料设置：

- 游戏昵称长度为 1～12 个字符；
- 玩家可以选择系统提供的默认头像；
- 玩家可以自愿选择微信提供的头像和昵称；
- 拒绝提供微信头像或昵称时，仍可使用自定义昵称和默认头像正常游戏；
- 昵称需要通过长度、空白字符、非法字符和敏感词校验；
- 服务端保存最终确认的游戏昵称与头像地址，不信任客户端绕过校验的资料。

### 6.3 资料修改与对局快照

- 玩家资料页首版只提供头像和昵称修改；
- 修改后的资料用于之后创建或加入的对局；
- 游戏开始时，将每名玩家当时的昵称和头像保存为本局玩家快照；
- 对局进行中修改个人资料，不改变该对局内已经锁定的昵称和头像；
- 对局记录继续使用开局时的资料快照，避免历史记录随个人资料修改而变化。

### 6.4 隐私与账号数据管理

- 小程序发布时提供明确的隐私说明，说明微信身份、昵称、头像、对局记录及网络状态等数据的用途；
- 仅收集登录、联机和对局留存所必需的数据；
- 客户端不得存储其他玩家的私密手牌、现金或未揭晓暗标报价；
- 提供账号数据删除入口；
- 删除请求须经过身份确认，并按照产品公示的规则删除或匿名化个人资料及可关联数据；
- 为保证已完成多人对局账目的一致性，必要的对局公共结果可以匿名化保留，但不得继续关联到已删除账号的个人身份。

### 6.5 首版不包含的账号与社交功能

首版不包含：

- 手机号绑定；
- 游戏内好友系统；
- 私聊或群聊；
- 全服排行榜；
- 复杂战绩统计与成就系统；
- 跨设备账号绑定；
- 第三方账号登录。

## 7. 界面布局方向

### 7.1 核心游戏桌面

核心游戏页采用 **拍品聚焦型布局（方案 A）**，优先保证手机竖屏下的拍品识别和单手竞价效率。

页面从上至下分为以下区域：

1. **对局状态栏**：展示房间号、当前阶段、当前主持人、连接状态等摘要信息；
2. **玩家状态区**：以紧凑头像列表展示座次、在线状态、当前行动者及公开藏品数量，不展示其他玩家现金或手牌详情；
3. **当前拍品区**：作为页面主视觉，突出藏品图片、名称、系列、皇冠数、失窃标识和竞拍方式；联合拍卖时并列展示两张藏品；
4. **竞拍信息与操作区**：展示当前价格、当前最高出价者、服务端截止时间和当前玩家可执行操作；
5. **个人手牌区**：固定在页面底部，以折叠抽屉形式显示手牌数量，展开后供主持人选择藏品；
6. **辅助信息入口**：通过轻量入口查看五色藏品数量与累计单价、拍卖记录和完整玩家列表，避免主界面信息过载。

### 7.2 交互原则

- 当前必须完成的操作始终固定在拇指易触达区域；
- 倒计时使用服务端截止时间计算，并在临近结束时提供明显但克制的视觉提醒；
- 主持人、当前操作人、最高出价者和离线玩家必须具有不同的图形或文字标识，不能只依赖颜色区分；
- 私密信息只出现在当前玩家自己的界面中；
- 阶段结算采用独立覆盖层或页面，逐步展示系列排名、藏品收益、失窃罚款和余额变化；
- 重要金额变化同时展示原因、变化值和结算后余额；
- 联合拍卖、暗标等复杂模式沿用同一主页面骨架，仅切换拍品展示与操作面板，避免频繁跳转页面。

## 8. 首版页面范围与用户流程

首版采用最小可发布页面集合，共包含 8 个主要页面。复杂竞拍操作优先使用游戏桌面内的覆盖层完成，不为每一种竞拍方式单独创建页面。

### 8.1 登录与建档页

- 完成微信身份登录与游戏会话创建；
- 首次登录时设置游戏昵称和头像；
- 展示隐私说明与必要授权提示；
- 已有资料的玩家登录成功后直接进入游戏首页；
- 检测到进行中对局时，提示并优先恢复对局。

### 8.2 游戏首页

- 创建房间；
- 输入 6 位房间号加入房间；
- 接收微信分享参数并加入指定房间；
- 恢复进行中的对局；
- 进入规则说明和个人资料页面。

### 8.3 房间大厅页

- 展示房间号、成员座次、在线状态和准备状态；
- 支持微信分享邀请；
- 非房主玩家可以准备、取消准备或在开局前离开；
- 房主可以移除玩家并在满足条件后开始游戏；
- 房主离开时实时展示房主转移结果。

### 8.4 游戏桌面页

采用已确认的**拍品聚焦型布局（方案 A）**：

- 顶部显示房间号、阶段、主持人和连接状态；
- 紧凑展示所有玩家的座次、在线状态、当前行动状态和公开藏品数量；
- 页面中央突出当前一张或两张拍品；
- 下方固定显示竞拍状态、服务端倒计时和当前玩家可执行操作；
- 页面底部使用可折叠手牌抽屉；
- 复杂竞拍切换操作面板，不离开游戏桌面。

### 8.5 阶段结算页

按顺序展示：

1. 五个收藏系列的本阶段数量排名；
2. 各系列本阶段新增单价与累计单价；
3. 玩家正常藏品收益；
4. 玩家失窃藏品罚款；
5. 负债冲抵过程；
6. 每名玩家结算后的现金净余额；
7. 银行回收和作废的藏品。

所有玩家确认或展示时间结束后，进入下一阶段；第 4 阶段结算后进入最终结果页。

### 8.6 最终结果页

- 按最终现金净余额从高到低展示排名；
- 相同现金净余额显示为并列名次；
- 并列第一的玩家全部标记为本局胜者；
- 展示本局房间号、参与者和结束时间；
- 支持返回首页。

### 8.7 规则说明页

规则按以下主题分区展示：

- 游戏目标与基础流程；
- 藏品属性；
- 五种竞拍方式；
- 阶段结束与价值结算；
- 失窃藏品与负债；
- 掉线、超时和重连规则。

规则说明页可从首页和游戏桌面打开。

### 8.8 个人资料与历史记录页

- 修改游戏昵称和头像；
- 查看已结束对局的日期、参与人数、最终余额和名次；
- 查看单局最终结算摘要；
- 查看隐私说明；
- 发起账号数据删除申请。

### 8.9 游戏桌面内覆盖层

以下功能通过游戏桌面内的弹层、抽屉或切换面板实现：

- 手牌浏览与主持人选择藏品；
- 联合拍卖模式选择、第二张藏品选择和联合邀请；
- 一口价定价；
- 公开竞价和顺序竞价报价；
- 普通及失窃藏品暗标报价；
- 五色藏品数量与累计单价；
- 完整玩家列表和公开已购藏品；
- 本局公开操作记录；
- 断线重连和状态同步提示。

### 8.10 主用户流程

```text
微信身份登录
  → 首次建档（仅首次）
  → 游戏首页
  → 创建房间 / 房间号加入 / 分享加入 / 恢复对局
  → 房间大厅与准备
  → 游戏桌面
  → 阶段结算
  → 下一阶段游戏桌面（重复至第 4 阶段）
  → 最终结果
  → 返回首页
```

异常流程包括：房间不存在、房间已满、对局已开始、玩家被移除、操作已过期、连接中断和重连恢复。所有异常均使用明确的页面内提示，并以服务端返回的最新状态为准。

## 9. 藏品数据与美术资源

### 9.1 首版素材策略

- 首版开发阶段使用本地占位图片，不等待 84 张正式藏品图片完成；
- 占位图片应能清楚区分黑、蓝、绿、黄、红五个收藏系列；
- 正常藏品使用白色边框，失窃藏品使用黑色边框；
- 占位图片仅用于开发和测试，不作为正式发布素材；
- 正式图片由产品方后续上传到 CDN，再通过配置替换；
- 正式素材应为原创、已授权或可合法商用的资源。

### 9.2 素材配置与替换入口

藏品业务数据和图片地址分离：

- 藏品 ID、名称、系列、皇冠数、竞拍方式和失窃状态属于固定业务配置；
- 图片资源通过独立的素材映射表按藏品 ID 关联；
- 页面组件只读取统一解析后的 `imageUrl`，不直接硬编码本地路径或 CDN 地址；
- 开发环境可使用本地占位资源；
- 测试和生产环境可切换为 CDN 基础地址或完整 CDN URL；
- 图片加载失败时回退到对应系列的通用占位图，不影响对局继续进行。

实现时在集中式素材配置或资源解析模块中保留统一注释：

```ts
// TODO(CDN_ASSET): 正式藏品图片上传 CDN 后，在此替换资源映射或 CDN 基础地址。
```

该注释只放在明确的集中替换点，不在每个页面或 84 张藏品调用处重复散落。

### 9.3 图片命名和缓存

- 建议正式文件名包含稳定的藏品 ID，不依赖可能修改的中文名称；
- 建议使用类似 `collections/{collectionId}/{assetVersion}/{itemId}.webp` 的 CDN 路径；
- 素材映射包含版本号，替换图片时通过版本路径或查询参数刷新缓存；
- 列表缩略图和拍品大图可以使用不同规格，减少小程序流量与首屏加载时间；
- 藏品图片不参与任何规则判定，系列、稀有度、竞拍方式和失窃状态全部以服务端业务配置为准。

### 9.4 临时牌库配置

首版使用已生成的测试牌库：[`docs/data/placeholder-collections.json`](./data/placeholder-collections.json)。

该牌库包含 84 张具有唯一 ID 和临时名称的藏品，并采用相对均衡的稀有度与竞拍方式配比。每个系列暂设 3 张失窃藏品，共 15 张；所有失窃藏品的竞拍方式都固定为暗标。普通藏品仍可使用暗标，因此“暗标”不等同于“失窃”。

这份配置作为规则引擎和联机测试数据使用。正式数据到位后可以替换名称、属性和图片映射，但必须继续满足固定牌库数量及规则约束。

### 9.5 数据校验

构建或服务启动时，应校验固定藏品配置：

- 藏品总数必须为 84；
- 各系列数量必须分别为黑 15、蓝 16、绿 17、黄 18、红 18；
- 每个藏品 ID 必须唯一；
- 皇冠数必须在 1～5 之间；
- 竞拍方式必须属于五种合法类型之一；
- 所有失窃藏品的竞拍方式必须为暗标；
- 联合拍卖藏品本身不得标记为失窃藏品；
- 每个藏品必须能够解析到正式图片或回退占位图。

## 10. 测试策略、部署环境与发布流程

### 10.1 规则引擎单元测试

独立的 TypeScript 规则引擎必须具备自动化单元测试，至少覆盖：

- 3～8 人的初始发牌与第 2、3 阶段补牌数量；
- 84 张固定牌库的唯一性、系列数量及属性约束；
- 五种竞拍方式及普通/失窃暗标分支；
- 报价资格、现金上限、最低报价、最低加价和超时默认行为；
- 主持人自行购得、其他玩家购得以及联合拍卖的三类现金结算；
- 联合拍卖奇数金额的向上、向下取整分账；
- 普通暗标最高价平局和失窃暗标最低价平局；
- 同系列第 6 张藏品及联合拍卖两张藏品的阶段结束判定；
- 五色数量排序、同数量颜色优先级和跨阶段累计单价；
- 正常藏品收益、失窃藏品罚款、负余额和后续收入冲抵；
- 主持权轮转、联合拍卖跳位和阶段间主持权；
- 全员手牌耗尽时的阶段结束；
- 最终现金排名、并列名次和多名胜者。

规则引擎测试不依赖微信环境、网络、MySQL 或 Redis，以便快速、确定地验证玩法。

### 10.2 服务端集成测试

服务端自动化测试至少覆盖：

- 登录会话、创建房间、房间号加入、准备、开始和房主转移；
- 游戏开始后的房间锁定和原玩家重连；
- WebSocket 连接、订阅、广播、断开和恢复；
- 根据玩家身份生成公开视图和私密视图，确保手牌、现金和未揭晓暗标不泄露；
- `requestId` 幂等处理与 `stateVersion` 冲突拒绝；
- 同一房间内并发操作的串行化；
- 服务端计时器、超时任务重复触发保护和重启恢复；
- Redis 快照、MySQL 事件日志、持久化快照和事件重放；
- 每笔现金变化的来源、去向及前后余额记录。

### 10.3 自动整局模拟

构建无界面的自动玩家，对以下人数分别执行可重复的完整对局模拟：

- 3 人；
- 4 人；
- 6 人；
- 8 人。

模拟应覆盖四个阶段、不同竞拍方式、联合拍卖、失窃罚款、负债、掉线超时和最终排名。测试使用固定随机种子，使失败能够稳定复现，并校验每局结束后藏品归属、现金总账、事件序号和状态机均合法。

### 10.4 小程序端测试

- 对登录、建档、首页、房间大厅、游戏桌面、阶段结算和最终结果等关键页面进行组件或逻辑测试；
- 测试不同屏幕尺寸和安全区域下的竖屏布局；
- 测试手牌抽屉、报价输入、倒计时、联合邀请和暗标揭晓等核心交互；
- 测试前后台切换、弱网、断网、WebSocket 重连和状态整体覆盖；
- 使用微信开发者工具完成真机预览前检查，并在至少两种实际移动设备尺寸上试玩。

### 10.5 环境划分

项目采用三套彼此隔离的环境：

| 环境 | 用途 | 数据策略 |
|---|---|---|
| 开发环境 | 本地开发、规则调试与自动测试 | 使用测试账号、占位素材和可重置数据 |
| 测试环境 | 多人联调、真机试玩和发布前验收 | 独立云资源，不与生产数据互通 |
| 生产环境 | 正式发布的小程序对局 | 正式域名、独立数据库、监控与备份 |

每套环境使用独立配置和密钥。敏感配置不得提交到代码仓库，也不得由小程序客户端持有数据库或 Redis 凭证。

### 10.6 分阶段发布流程

1. 在开发环境完成规则引擎、服务端和小程序功能；
2. 运行单元测试、集成测试及 3/4/6/8 人自动整局模拟；
3. 部署到微信云托管测试环境；
4. 使用微信开发者工具和真机进行多人试玩；
5. 修复问题后执行完整回归测试；
6. 配置正式小程序、生产云托管、数据库、Redis、对象存储和合法域名；
7. 完成隐私说明、用户数据删除入口及发布材料；
8. 提交微信小程序审核；
9. 审核通过后发布生产版本，并持续观察错误率、连接状态和异常对局。

### 10.7 发布门槛

正式发布前至少满足：

- 所有规则引擎单元测试通过；
- 服务端核心集成测试通过；
- 3、4、6、8 人自动模拟均可完成整局；
- 不存在可复现的重复扣款、重复成交、手牌泄露或暗标泄露；
- 断线重连后状态与服务端一致；
- 测试环境完成至少一轮 3～8 人真人试玩；
- 生产环境具备结构化日志、错误监控、健康检查和数据库备份。

## 11. 首版范围边界

首版定位为供微信好友小范围开房游玩的测试版本，以验证完整规则、实时联机稳定性和移动端操作体验为目标，不追求公开运营所需的完整商业化与社区能力。

### 11.1 首版必须包含

- 微信身份登录与最小玩家资料；
- 创建房间、6 位房间号加入和微信分享加入；
- 3～8 人准备、开局和房主的开局前管理；
- 固定 84 张测试牌库与本地占位图片；
- 四阶段完整游戏流程；
- 五种竞拍方式及所有已确认的特殊规则；
- 服务端权威计时、规则校验和现金结算；
- 玩家私密信息隔离；
- 掉线检测、超时托管和同账号重连；
- 阶段结算、最终排名与并列胜者；
- 已完成对局的基础历史结果；
- 开发、测试环境及好友多人试玩能力。

### 11.2 首版明确不包含

- AI 玩家和单机模式；
- 匹配大厅和陌生人随机匹配；
- 观战、录像回放与对局内聊天；
- 好友、公会和全服排行榜；
- 商城、充值、广告及其他付费功能；
- 自定义房间规则；
- 管理后台和在线牌库编辑器；
- 横屏、平板和 PC 专用布局；
- 语音、视频和实时通话；
- 对局暂停和主动退赛；
- 正式 84 张藏品美术资源。

### 11.3 首版验收目标

首版在进入小范围好友试玩前，需要做到：

1. 3～8 名微信用户能够通过分享或房间号进入同一房间；
2. 玩家可以从开局连续完成四个阶段并得到正确最终排名；
3. 五种竞拍方式、联合拍卖、失窃罚款与负债规则均可正常执行；
4. 手牌、现金和未揭晓暗标不会泄露给其他玩家；
5. 短暂断线后可以回到原座位并恢复服务端最新状态；
6. 关键规则具备自动化测试，3、4、6、8 人模拟对局可以完成；
7. 使用占位素材即可完成真机多人试玩，正式 CDN 图片不阻塞首版测试。

## 12. 后续版本候选能力

首版试玩稳定后，再根据反馈决定是否增加正式美术、战绩统计、观战回放、好友关系、匹配系统、聊天、AI 玩家、运营后台或商业化功能。这些能力不纳入当前实施计划，也不得延误首版测试版本交付。
